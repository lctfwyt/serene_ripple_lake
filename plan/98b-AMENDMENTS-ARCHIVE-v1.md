# 变更单（Amendments）—— 跨工作包的追溯修改通道

> **每个新聊天框开工前先读本文件。** 若「变更总表」里有影响你那个包的未决条目，
> 先应用它，再干本包的活；应用完把状态改成 `✅ 已应用`。

## 0. 这个文件为什么存在

拆分多聊天框以后，**只有两份文件能跨窗口传话**：`01-CONTRACT.md`（冻结的签名）和本文件。

而这次暴露了一个盲区：`01-CONTRACT.md` 只管**函数签名 / 字段名 / DOM id**，
**不管数值约定**。像「相机俯角」「水位 y」「湖底尺寸」这些东西，原先写在
`10-WP1-*.md` 的正文里 —— WP1 完成后没人再看那个文件，于是：

- WP2 会按自己的理解定水面尺寸
- WP3 会按自己的理解定"地平线在哪"
- 合并时才发现对不上，而代价已经付掉了

**变更单就是补这个洞的通道。** 三条规则：

| 规则 | 内容 |
|---|---|
| **1 · 数值约定进契约** | 凡是 ≥2 个 WP 要依赖的数值，一律提升到 `01-CONTRACT.md **§9 共享常量**`。**不允许只写在某个 WP 的正文里。** |
| **2 · 追溯修改走变更单** | 已发出的 WP 要改，在下面开一条 `AM-xxx`，写全「影响面 + 逐包动作 + 断言变更」。 |
| **3 · 横幅指向变更单** | 受影响的 WP 文档顶部加一行 `> ⚠️ 未应用变更单：AM-xxx`。新聊天框只读三份文件，**横幅是唯一能进它视野的通道。** |

# AM-001 · 机位改「高俯视 · 全湖面 · 无地平线」

> **提出人**：雨桐（2026-09-23）
> **原话**：「相机角度我也想高一点，更俯视，让网页都是湖水，不要看到地平线上方部分。」
> **状态**：✅ 已应用（2026-09-23 23:38，WP1b 完成代码部分）　**优先级**：🔴 阻塞 —— 已解除，WP2 / WP3 可开工
> ⚠ WP2 / WP3 / WP5 文档顶部的横幅仍指向本条：你们的 §4.2 / §4.3 / §4.4 **约束项**仍须遵守（那是开工前必读，不是待应用的代码改动）。

## 1. 背景：这条变更同时解决 WP1 遗留的两处冲突

`plan/_STATUS.md` 里 WP1 留了 2 处规格冲突等裁决。**AM-001 一次解决两条**，所以不必再单独裁决：

| 原冲突 | 原问题 | AM-001 如何解决 |
|---|---|---|
| **冲突 1** | 相机 `y=1.15` 在水面 `y≈1.55` **之下** → 无法俯视湖面，WP2 的「透过水看见扭曲鹅卵石」在数学上做不出来 | 相机抬到水面**之上 4.35**，彻底解决 |
| **冲突 2** | 「地平线落在 0.42–0.50」与「俯角 12–18°」互斥（地平线行位只由俯角决定）；要满足 0.42 得把雾加到 `density≈0.30`，画面会变「浓雾」而非「湖」 | **地平线直接被推出画面外**，这条判据作废 —— 冲突消失 |

**冲突 2 的那个数字不要去满足了。** 新的判据是「地平线不可见」。

## 2. 变更前后对照

| 项 | 变更前（WP1 已交付） | 变更后 | 理由 |
|---|---|---|---|
| `fov` | `42` | **`34`** | 42 太宽：高俯视时画面纵向跨越 4→50 单位的水面，上半屏全是雾。34 把取景收进 5→31 单位的中景带 |
| `camera.position` | `(0, 1.15, 3.4)` | **`(0, 5.9, 3.4)`** | 水面之上 **4.35**（`WATER_Y=1.55`） |
| `lookAt` 目标 | `(0, -1.438, -6.259)` | **`(0, 1.55, -5.93)`** | 水平前视 9.33 单位、落回水面高度 |
| 俯角 | `15°` | **`25°`** | 见 §2.1 —— **必须 > 17°**（= fov/2）才能让地平线出画面 |
| 地平线行位 | 实测 `0.210` | **理论 `-0.235`**（画面外） | 见 §2.2 验算 |

### 2.1 为什么俯角必须 > 17°

fov=34 → **垂直半角 = 17°**。画面顶边对应的射线俯角 = `俯角 − 17°`。

| 俯角 | 顶边射线 | 地平线 | 结果 |
|---|---|---|---|
| 15° | 向上 2° | 画面内 | ❌ 看得到天空 |
| **17°** | **水平 0°** | **正好压在顶边** | 临界，抖动会露头 |
| **25°** | **向下 8°** | **画面外 23.5%** | ✅ **采用**，余量 8° |
| 30° | 向下 13° | 画面外 38% | 可以，但近处压缩变重 |

**25° 是余量与构图的平衡点**：余量 8° 足够吃住窗口拉伸、UI 遮挡、呼吸位移（`P.cameraSway`）；同时还没到「俯拍地图」的观感。

### 2.2 验算（可复现）

```
俯角   = atan((CAM_Y − WATER_Y) / LOOK_AHEAD)
       = atan((5.9 − 1.55) / 9.33) = atan(0.4662) = 25.00°   ✓
地平线 = 0.5 − 俯角 / fov = 0.5 − 25/34 = −0.235            ← 负值 = 在画面顶边之外
顶边射线俯角 = 25 − 34/2 = 8°（向下）                        ← 全程俯视水面，无天空
```

画面覆盖的水面纵深（相机在 `z=3.4`，朝 `−z` 看）：

| 画面位置 | 射线俯角 | 水平距离 `4.35/tanφ` | 世界 `z` |
|---|---|---|---|
| 顶边 | 8° | 30.9 | −27.5 |
| 中线 | 25° | 9.33 | −5.93 |
| 底边 | 42° | 4.83 | −1.43 |

**湖底 `BED_SIZE = 90`（`z ∈ ±45`）足够覆盖到 `−27.5`，不会露边。**
且 `z=−13` 以外已在雾里淡出 —— 雾的角色从「遮住地平线」变成**「让远处水面自然淡出」**，依然必要，**不要因为看不到地平线就调稀雾**。

## 2. 🟢 建议采纳 A · 反光路径（glitter path）—— 落到 WP2 + WP3

### 2.1 它为什么值得做

不是因为"好看"，而是因为它**正好补上 AM-001 移走天空后留下的表达缺口**：

| AM-001 的后果 | glitter path 如何补 |
|---|---|
| 看不到天空 → 星夜没有"星星"可挂 | 月光柱就是夜景的视觉焦点 |
| 四态差异只能落在水面/雾色上，容易做成"换了颜色的一潭水" | 柱的方向（时间）、色温（时段）、强度（天气）天然随时段变化 |
| WP1b 已报告**画面亮度带收窄到 157–196、偏闷** | 柱提供一条高亮度通道，直接把直方图右端拉开 |

**这三条是"不做也得做"的理由** —— 不是锦上添花。

### 2.2 技术方案

核心是 **GGX 镜面高光 + 两层法线**：

```
大尺度：波动方程 FBO 的波纹法线（已有，WP2 产出）  → 负责柱的"摆动"
小尺度：高频程序化细节法线（新增）                  → 负责柱的"破碎/颗粒感"
```

**⚠️ 只有大尺度波纹是做不出柱的** —— 高光会连成一条光滑的带子，像塑料。截图里那种
一格一格的破碎感，**必须靠高频细节法线**。这是本条最容易做砸的地方。

```glsl
// 在 WP2 的水面 fragment shader 里
vec3 N = normalize(vec3(0.0, 1.0, 0.0)
         + rippleNormal * uNormalGain              // 大尺度（已有）
         + detailNormal * uGlitterDetail);          // 小尺度（新增）
vec3 H = normalize(V + L);
float spec = D_GGX(dot(N, H), uGlitterRough) * F_Schlick(dot(V, H)) * G_Smith;
```

| 新参数 | 建议初值 | 作用 |
|---|---|---|
| `glitterDetail` | `0.35` | 颗粒感强度。0 → 光滑塑料带；过大 → 噪点闪烁 |
| `glitterRough` | `0.045` | **柱的锐利度**。`0.02` 极细亮线 · `0.08` 宽柔光带 |
| `glitterGain` | `1.0` | 总体强度，由 WP3 按时段驱动（夜晚最强、正午最弱） |
| `glitterJitter` | `0.15` | 法线随时间的微抖，让柱"活"起来 |

**去闪烁**：单次采样在运动时会有高频爆闪。取 **3 个不同相位**的 `detailNormal` 求平均
即可（成本 ×3，但只是几个 `sin`，可接受）。或对 `glitterRough` 做轻微模糊。

**必须做的一步**：`detailNormal` 的尺度要与波纹法线**归一化配平**。
两者尺度不匹配 → 柱会"在波纹上乱跳"。WP2 需要显式调这个配比。

### 2.3 落到 WP3 的部分

`glitterGain` / `glitterColor` 由 `TimeState` 驱动。建议每个时段键给一组：

| 时段 | `glitterGain` | `glitterColor` | 说明 |
|---|---|---|---|
| 晨雾 | 0.35 | 暖白偏黄 | 低角度晨光，柱偏短偏散 |
| 正午 | 0.15 | 白 | 高角度 → 柱几乎消失，只有碎光 |
| 黄昏 | 0.85 | 琥珀金 | **最强**，暖金光柱 |
| 星夜 | 1.00 | 冷白偏蓝 | 月光柱，截图就是这个状态 |

> **注意**：这 4 组是**新增的 TimeState 字段**，要同步 `01-CONTRACT.md §2.2` 与 §9。
> 若雨桐裁决采纳，这一步由契约变更处理。

## 2. 🔴 新增修正 1：光源仰角必须恒为正 —— 与 AM-001 §4.3 第 5 条冲突

**这是本次最要紧的一条。WP2 没报，是复算时算出来的。**

`WP3 §4.4` 现在的公式：`sunElev = sin((hour − 6)/12 · π) × 65°`

| 时刻 | 5.5h（晨雾） | 12.5h（正午） | 18.5h（黄昏） | 22.5h（星夜） |
|---|---|---|---|---|
| 公式给出 | **−8.5°** | 64.4° | **−8.5°** | **−60.0°** |

而 `60-water.js` 的 `glitterSpec()` 第一道门就是 `if (Ly <= 0.02) return 0`。

**后果：按现在的公式，晨雾 / 黄昏 / 星夜三个时段的反光柱全部为 0，只有正午有 0.002。AM-002 的整个 A 项在夜间等于没做。**

原因是 **AM-001 §4.3 第 5 条**：

> 「夜间必须有 `sunElev < 0` 时 `sunIntensity = 0`，否则出现地平线下照上来的假光」

**这条必须改。** 它本身没错，但它把"夜间"当成了"太阳落到地平线以下" —— 而 AM-002 的夜景要的是一颗
**挂在地平线之上 25~30° 的月亮**。两条变更单在这一点上是矛盾的，**以本条为准**。

| 项 | 旧（AM-001 §4.3-5） | 新（AM-003） |
|---|---|---|
| 夜间光源 | `sunElev < 0` + `sunIntensity = 0` + hemi 接管 | **`sunElev ∈ [22°, 30°]`**（月亮）+ 冷色 + **`sunIntensity ≥ 0.6`** |
| 「假光」防线 | 靠 `sunElev < 0` 判断 | 改成 **「`sunElev` 永不为负」**，断言直接钉住（§5.3 第 5 条） |

`60-water.js` 里 WP2 埋的 `SUN_I_FLOOR = 0.30` 因此**只是安全网，不是设计方案**：
它让 `glitterSpec`（probe 不含辐射度）照样读到 1.0，**但画面上的柱只有 0.30 的亮度 → 会假通过**。
所以 §5.3 必须同时检查 `SW.scene.sun.intensity`。

## 3. 🔴 新增修正 2：方位约束改成「随宽高比夹取」，不能写死角度

`SUN_AZ_SECTOR`（契约 §9 现值 `±75°`）**连 `±25°` 都不能写死** —— 竖屏下安全区只有 12.73°。

**改成公式 + 运行时夹取**（WP3 一行代码）：

```js
// 相机水平半视角（视口变化时重算）
var hHalfDeg = Math.atan(Math.tan(fov / 2 * Math.PI / 180) * camera.aspect) * 180 / Math.PI;
// sunAz 相对相机朝向（π）的最大允许偏角
var kDeg = Math.min(22, Math.max(7, hHalfDeg - 6));   // 6° 余量；7° 是竖屏的保底下限
sunAz = Math.PI + clamp(rawAzOffset, -kDeg * Math.PI / 180, kDeg * Math.PI / 180);
```

| 窗口 | `hHalf` | `kDeg` | 说明 |
|---|---|---|---|
| 16:9 桌面 | 28.03° | **22°** | 上限封顶，柱距画面边还有 6° |
| 16:10 笔记本 | 25.66° | **19.7°** | 自动收窄 |
| 方形 | 16.40° | **10.4°** | |
| 竖屏 | 12.73° | **7°** | 12.73 − 6 = 6.73 → 保底到 7 |

**⚠️ 夹取必须发生在 `getState()` 内部**（产出 `TimeState` 时就夹），不能只在 `applyTimeState` 阶段夹。
否则 `probe().sunAz`（读的是 `TimeState`）与实际光源位置不一致 —— WP5 的断言会读到没夹过的值。

## 2. 变更方案

### 2.1 场形状：圆盘 → 可见梯形（拒绝采样）

```js
// 40-lakebed.js —— 契约 §9 + §6 给数，不再用 pebbleArea 圆盘
var F = SW.P.pebbleFieldZ;          // [NEAR_Z, FAR_Z] = [-3.0, -24.0]
var W = SW.P.pebbleFieldHalfW;      // [HALF_W_NEAR, HALF_W_FAR] = [4.51, 14.85]
function halfWidthAt(z) {
  return W[0] + (W[1] - W[0]) * (F[0] - z) / (F[0] - F[1]);
}
function inField(x, z) { return Math.abs(x) <= halfWidthAt(z); }
// 拒绝采样 → 面积均匀（不是按 x/z 各自均匀）
do { z = F[0] + rand() * (F[1] - F[0]);
     x = (rand() * 2 - 1) * W[1]; }     // 用最大半宽兜上包络
while (!inField(x, z));
```

**为什么取 `NEAR_Z = −3.0`**：近边实测 −3.15，往外放 0.15 是为了避免画面底边出现「石头戛然而止」的横线。
**为什么取 `FAR_Z = −24`**：该处雾穿透率 < 15%，再做无意义。

**采样用拒绝法而不是分别均匀**：梯形远段半宽是近段的 3.3 倍，若 `x`、`z` 各自均匀，远段单位面积密度会被摊薄成 1/3，近处会显得过密。

### 2.2 双层 LOD

|---|---|---|---|---|---|
| L0 近景 | `[−3.0, −11]`（面积 103.6） | `Icosahedron(1, 2)` = **180** | **88** | 15,840 | **0.85 /单位²** |
| L1 中远景 | `[−11, −24]`（面积 302.8） | `Icosahedron(1, 1)` = **80** | **150** | 12,000 | **0.50 /单位²** |
| L2 远景 | `< −24` | **不生成** | 0 | 0 | — |
| | | | **238** | **27,840** | |

**预算复核**：`43,248 − 18,000 + 27,840` = **53,088 tris** ✓（余 6,912）· calls **6** ✓（余 2）

**清晰带（z ∈ [−3, −14]，面积 158.8）内有效密度 ≈ 0.73 颗/单位²** —— 落在参考图 0.5~1.0 区间中段。相比现状 0.033 是 **×22**。

**砍掉 AM-002 §6 的 L2 程序化法线贴图层**：那一层要改湖底材质的 `onBeforeCompile`，而 z < −24 处雾穿透率 < 15%，收益为零、风险非零。

### 2.3 配色：单色抖动 → 5 档调色板

| 名 | hex | sRGB 亮度 | 权重 |
|---|---|---|---|
| 深青石（玄武） | `#4f5b57` | **0.34** | 0.16 |
| 冷灰石 | `#78857f` | 0.50 | 0.30 |
| 中灰石 | `#9a9f95` | 0.61 | 0.27 |
| 暖米石（砂岩） | `#b8a992` | 0.67 | 0.17 |
| 浅石英 | `#d8d7cc` | **0.84** | 0.10 |

亮度极差 **0.50**（现状 0.153，**×3.3**）。权重做成「中间多、两端少」的钟形 —— 两端的石头才显眼。

**⚠️ 两个必须遵守的实现细节**

1. **`material.color` 改成纯白 `0xffffff`，`aTint` 直接放「线性空间」的调色板色**。
   这样 `diffuseColor = white × lin(palette)`，语义最干净，且 `aTint` 恒 ≤ 1（不需要 >1 的值）。
2. **不许把 sRGB 数值直接写进 `aTint`。** r160 的 `ColorManagement` 默认开启，
   `diffuseColor.rgb *= vTint` 发生在线性空间。把 sRGB 值当线性值写进去，暗石会偏亮、
   整体发灰、对比被吃掉。正确做法：
   ```js
   var c = new THREE.Color().setHex(hex, THREE.SRGBColorSpace);  // 得到的就是线性值
   tint[k*3] = c.r; tint[k*3+1] = c.g; tint[k*3+2] = c.b;
   ```
3. **暗端下限 0.34（sRGB 亮度）**。湖底基色是 `#5d6f66`（亮度 0.42），比它更暗的石头会在
   水下吸收（`Beer-Lambert`，水深 1.55）之后和湖底阴影糊在一起，反而看不出来。`#4f5b57` 是安全下限。

**顺带放宽 `aRough`：[0.35, 0.70] → [0.22, 0.80]**。暗石略亮（湿石感）、浅石偏哑 ——
**零成本再翻一倍质感差异**，因为这条路径只改一个取值区间。

### 2.4 「只改取值范围、不增删 `rand()` 调用」

`aTint` / `aRough` 是从 `SW.util.mulberry32(P.seed)` 的顺序流里取的。**每实例的 `rand()` 调用次数必须保持不变**，否则后续所有颗的位置全部漂移，`_STATUS` 里已验证过的「实例矩阵零重复」要重验。

改法：只动 `rg(rand, lo, hi)` 的 `lo/hi`，不动调用位置与次数。调色板选择额外需要 1 次 `rand()` —— **允许，但要写在 `aTint` 赋值那一行**（同一处增删，便于审查）。

# AM-005 · caustic 强度随昼夜调制（+ 两条评估结论）

> 提出：WP1d · 2026-09-24 01:50 · 起因：雨桐问「一天不同时间的光影能否自然」
> 状态：**WP1 已落地**（`caustics` 仍为 `false`，像素输出零变化；机制待命）

## 1. 实测依据（4 时段，只留湖底平面，亮度 std = 波纹强度）

| 时段 | sunI | 固定 `causticStrength=0.5` | 昼夜调制后 | 因子 |
|---|---|---|---|---|
| 晨雾 5.5 | 0.90 | mean 129.8 · std **25.4** | mean 114.2 · std **18.9** | ×0.381 |
| 正午 12.5 | 2.10 | mean 154.0 · std **28.5** | mean 154.0 · std **28.5** | ×1.000 |
| 黄昏 18.5 | 1.30 | mean 125.1 · std **30.7** | mean 115.0 · std **25.8** | ×0.640 |
| 星夜 22.5 | 0.70 | mean 95.3 · std **33.1** | mean 60.1 · std **12.4** | ×0.151 |

🔴 **固定强度的分布是反的** —— 夜间 std 最大（33.1 > 正午 28.5），因为 caustic 是加性发光，
在暗底上对比反而更强 → 星夜湖底铺着一层和正午一样亮的水波纹。调制后恢复「正午最强、夜间最弱」。

## 2. 变更

| 项 | 内容 |
|---|---|
| 契约 §6 | 加 `causticDayMod: true` · `causticNightFloor: 0.08`；**`causticStrength` 语义由「固定强度」改为「峰值」** |

## 3. 评估结论 A：❌ 用「铺满鹅卵石的图片」替换/补充几何石 —— 在本项目**不可行，且不划算**

**硬性阻断（实测，`--headless` 无 `--allow-file-access-from-files`，即**双击打开的真实场景**）：**

| 路径 | 结果 |
|---|---|
| `img.onload` | ✅ ok（256×256，图片元素能读到） |
| 2D canvas `getImageData` | ❌ `SecurityError`（canvas 被 taint） |
| `THREE.Texture(img)` → `initTexture` | ❌ `SecurityError: Failed to execute 'texSubImage2D' … The image element contains cross-origin data, and may not be loaded.` |
| `THREE.TextureLoader().load()` | ❌ `onError` |

`file://` 下外部图片**进不了 WebGL 纹理**。绕开只有两条，均违反 §5 全局技术决策：
① base64 内联（1K JPG ≈ 400KB 文本；2K normalMap 更大，且违反「不内联大文件」）；
② 起本地服务器（丢掉「双击打开」这一交付形态）。

**就算能加载也不划算**：
- 俯角 25° → 视线与湖底法线夹 **65°，掠射**。平面 `normalMap` 在掠射角下会糊、uv 拉伸明显；照片贴图**没有剪影、没有相互遮挡、没有视差**，而「密铺鹅卵石」的读感恰恰主要来自这三样。
- 可见区纵深 21 单位、半宽 4.51→14.85，铺满要 repeat 很多次 → **照片类纹理重复 >6 次就肉眼可辨**。
- 成本反升：现状 **238 实例 / 53,088 tris / 6 draw calls**；换 2K albedo+normal+rough ≈ **16MB 显存 + 移动端带宽**，calls 也不减。
- 动态光照下假法线在 `sunElev 22°→64°`、`sunI 0.7→2.1` 的大幅变化时会穿帮。

**而且不解决问题**：去水静帧显示湖底石头深浅三档（暗板岩 `#4f5b57` / 中灰 `#9a9f95` / 暖砂岩 `#b8a992`）已肉眼可辨 —— 短板不在这里。
（可借用的是**程序化 canvas 纹理**给远景补密铺底噪，不是替换近景几何；且 §6 已明确不做 L2 法线层。）

# AM-006 · 收窄夜间白光（glitter path）范围

> 提出：雨桐 · 2026-09-24 02:44  
> 状态：**已应用** · 责任 WP2（`60-water.js` 实现 + `SW.P` 参数语义）

## 1. 问题

WP3 交付后夜间出现反光柱，但**白光铺得整片水面都是**，读不出「一条月光带」。

## 2. 根因

`SW.P.glitterDetail = 0.35` 让细节法线 RMS 斜率达到约 **19°**，而 GGX alpha 由 `glitterRough 0.045` 决定，瓣宽约 **5.6°** —— 法线摆动是瓣宽的 3.4 倍。结果是：

- 全画面任何像素都有不可忽略的概率「误中」镜面方向；
- 真正的镜面线只是提高了概率，而不是显著提高亮度；
- 人眼看到的就是均匀撒在水面的碎白光（`_STATUS.md`「WP3 遗留」已记录）。

## 3. 变更

| 项 | 内容 |
|---|---|
| 契约 §6 | `glitterDetail: 0.35 → 0.16` · `glitterRough: 0.045 → 0.065` |
| `00-config.js` | 同上，并加 AM-006 语义注释 |
| `60-water.js` | 加 `uProbe = 8` 诊断通道（D·Vis·Fs），不改渲染逻辑 |
| 契约影响 | `glitterSpec()` 只变 alpha，几何位置不变；断言阈值不变 |

## 4. 理由

- `glitterDetail 0.16` → RMS 斜率约 **9°**，是瓣宽（~7.4°）的 1.2 倍。镜面线附近仍有足够法线「对上」，但远离镜面线的误中概率大幅下降，碎白光从「满屏」收束到柱周围。
- `glitterRough 0.065` → 单颗高光从针尖扩成小圆斑，避免柱断成断续散点，保持一条可读的连续光带。
- 低于 0.12 会退回到光滑塑料带；高于 0.22 又会重新铺开。

## 2. A · LOD 尺度统一（WP1e）

> **🔴 2026-09-24 修订（主控直裁 + 实测）**：本节初版的改法**写错了一半** —— 只改了 `pebbleScaleFar`，
> 却声称「与 near `[0.14, 0.42]` **同一区间** → 中位比 **1.0**」。`[0.20,0.58]` 的中位是 0.39，
> near 是 0.28，比值为 **1.393**，自相矛盾。WP1e 执行后按判据一测就暴露了。
> **正确改法是两层都取 `[0.20, 0.58]`**（这也正是 WP1d-fix 遗留③的原始建议）。
> 下方 §2.1–§2.3 是修订版，含实测依据。

### 2.1 现象与根因

**现象**：夜间静帧里，画面**中下部的石头明显大于底部近处的石头**。

**根因**：`pebbleScaleNear [0.14, 0.42]`（中位 **0.28**）vs `pebbleScaleFar [0.35, 0.80]`（中位 **0.575**），
远层是近层的 **2.054×**。WP1d-fix 按裁决只改了近层（为破「凝胶团块」），**远层没跟着改**，两层世界尺寸不再匹配。

### 2.2 三个口径各自量什么（⚠️ 这决定了改法）

| 口径 | 量什么 | 随尺寸变吗 | 现状读数 |
|---|---|---|---|
| `pebbleDensity` | **颗数** / 面积 | ❌ **不变** | 0.787 ✅ 达标 |
| `pebbleCoverage` | **足迹面积** / 面积 | ✅ 平方关系 | **0.235** ← 稀 |
| `LOD 接缝比` | 两层**屏幕尺寸分布**的中位比 | ✅ | **1.125** ← 倒挂 |

**这就是 WP1d-fix 的教训**：它把近景缩小后「石头变稀、露底多」，而当时唯一的量化判据是 `pebbleDensity` ——
**量颗数的判据对尺寸改动完全不敏感**，所以三条断言全过、观感却错了。
→ 契约 §9 因此补了 `PEBBLE_COVERAGE_MIN` 与 `PEBBLE_LOD_SEAM_RATIO_MAX` 两条。

### 2.3 🔴 判据必须是「分布口径」，不是「单颗口径」

**雨桐问得对**：每颗石子尺寸本来就随机，**远层一颗大石当然可以比近层一颗小石显得大** ——

```js
// 逐字段、逐相邻对取最大；KEYS 是环，最后一对要接回 KEYS[0]
const F = ['sun','sky','gnd','fog','wat','gli'];
const w = d => { d = ((d % 360) + 360) % 360; return d > 180 ? d - 360 : d; };
let mx = 0, where = '';
for (const k of F) for (let i = 0; i < K.length; i++) {
  const a = K[i][k], b = K[(i+1) % K.length][k];
  const s = Math.abs(w(b[2] - a[2])) * Math.min(a[1], b[1]);
  if (s > mx) { mx = s; where = k + ' ' + K[i].n + '→' + K[(i+1) % K.length].n; }
}
// 断言：mx < 2.5   （实测 2.11 = sun 斜阳→黄昏）
```

## 2. 实测依据（全部可复现，脚本 `_up5-measure.js` / `_up5-measure2.js`）

> ⚠️ **本机无 `ffmpeg` / `ffprobe`，Python 环境也没有任何音频库**（`pip install numpy soundfile pyloudnorm`
> 在镜像同一字节处**连续两次** `IncompleteRead` 截断）。
> → 改用**无头 Chrome 内解码 + 计算**：`fetch` → `decodeAudioData` → 在页面内实现
> **ITU-R BS.1770-4**（K 加权解析系数 + 400 ms 块 / 75% 重叠 + −70 LUFS 绝对门 + −10 LU 相对门）
> 与循环接缝包络。**零外部依赖，且量的就是浏览器实际解码的 PCM。**

### 2.1 `bgm-stillwater.mp3` 响度

| 项 | 实测 |
|---|---|
| 时长 / 采样率 / 声道 | **146.832 s** · 48000 Hz · 2ch |
| 采样峰值 | **0.9514**（−0.43 dBFS） |
| **集成响度（BS.1770-4）** | **−15.06 LUFS**（1465 块 / 绝对门 1465 / 相对门 1443，相对门限 −25.12） |

→ 距 −16 LUFS 目标 **+0.94 LU（偏响）** → `BGM_TRIM = 10^(−0.94/20) = 0.8974`。

### 2.2 拍击 4 段

| 段 | 时长 | 峰值 | **集成响度** |
|---|---|---|---|
| `slap1.wav` | 1.45 s | **0.62** | −20.27 LUFS |
| `slap2.wav` | 1.45 s | **0.62** | **−21.12 LUFS** |

### 2.3 `bgm-stillwater.mp3` 循环接缝 —— 🔴 **不是干净循环**

`_up5-measure2.js` 的 10 ms 窗口包络（dB）：

```
首 40×10ms: [-120, -139.7, -52.4, -46.3, -48.7, -49.7, -51.6, -55.6, -54.8, -52.7,
              -24.4, -13.7, -15.9, -18.1, -21.8, -23.5, ...]
尾 40×10ms: [-25.4, -26.8, ..., -27.5, -29.3, -32.7, -48.4]
首个 |x|>0.05 的样本：idx=5186 → t = 0.108 s
```

| 项 | 实测 | 判读 |
|---|---|---|
| **曲首** | `0~20 ms` 为**绝对零**（−120 / −139 dB），`20~100 ms` 仅 −46~−55 dB（≈量化噪声底），**0.108 s 才有第一个有效样本** | 🔴 曲首有 **~100 ms 数字静音** |
| **曲尾** | 一直有声（−25~−29 dB），**最后 10 ms 快速落到 −48.4 dB** | 尾端自带 ~10 ms 收尾 |
| 接缝一步跳变 `seamStep` | **3e−6**（轨内 p99.9 跳变 0.0247 → 比值 **0.0001**） | ✅ **波形连续：没有「咔」** |

**→ 结论：`el.loop = true` 不会"咔"，但会每 146.8 s 出现一次 ~100 ms 的静音塌陷**（一次"呼吸"）。
这正是 `90-WAVE4 §3` 第 4 条担心的那件事 —— 只是症状是**能量凹陷**而非爆音。
按「接缝前后 50 ms 能量差」口径：`head50 = −50.68 dB` vs `tail50 = −29.87 dB` → **20.81 dB** ❌

**修法（不改资产、不重编码）**：手动 loop 区间 `[0.20 s, 146.802 s]`（**右端 = 真实内容末端 − `LOOP_TAIL`**，
不是元素的估算时长末端 —— 见 §3.2 第 11 条），接缝两侧各加一段短淡入淡出。选 `0.20 s` 的依据是**首尾电平自动对齐**：
曲首 `[0.20, 0.25] s` 各 10 ms 窗 = −29.3 / −30.1 / −29.2 / −28.9 / −31.5 dB ≈ **−29.8 dB**，
而曲尾 50 ms = **−29.87 dB** → **天然只差 ~0.1 dB**。
