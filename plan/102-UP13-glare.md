### 1.3 🔴 一条必须先说清的**更正**：不是"近处更亮"

雨桐描述「不应该近处更亮」。**原始镜面项实测恰好相反**：

- 纵向 **远端 70.9 → 近端 29.3** ⇒ 物理上**本来就是远强近弱**
- 准确的说法是：**能量峰值堆在画面中段（42%~54% 高度，贡献 112），而画面最远端最弱（36）**

**为什么会这样（几何解释）**：镜面点距离 = `4.35 / tan(仰角)`。夜间仰角 **28°** ⇒ 镜面点在 **8.2 m**
（画面可见范围 4.83~30.95 m）⇒ **正落在画面中段**。而画面顶部（22~31 m）要求坡面倾角最小（约 18°），
在法线分布里属于**长尾**，所以最暗。

⇒ 要实现雨桐的「**从远处衍生到近处**」，只有两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| **① 观感整形（推荐）** | 给反光项乘一个**随视线距离单调递增的权重**（远端起、近端压）—— 纯整形，不动几何 | 新增 1 个参数；需复测 #13 |
| ② 改几何 | 把夜间仰角从 28° 降到 ~12° ⇒ 镜面点移到 20.5 m（画面中上部） | 🔴 **`#10` 冻结了低光时段仰角 ∈ [22°,30°] ⇒ 必须先开变更单**；且仰角越低镜面项越强（AM-003：22° 的 shape 7.63 vs 28° 的 2.50）⇒ 会连带更亮 |

### 1.4 夜间"碎网"来自哪里

夜间那张图（`plan/shots-up4/pv-clarity-directions.png` 第 2 行第 1 格）不是一条柱，而是一张**白色碎网**。
成因是两层法线一起进了 GGX：`uNormalGain 2.4`（大波纹 FBO）× `glitterDetail 0.16`（细节法线）
⇒ 局部平均法线被大波纹调制成"一格一格"（`60-water.js:273-275` 已注明这是**设计意图**：破碎感）。
⇒ 收窄它不是"清掉"网眼，而是**压幅度**（§2 的候选 2）。

### 1.6 🔴 2026-09-25 15:00 追加：雨桐给了参考图 —— 本包从「反光克制」升级为「月光柱形态重做」

雨桐给了一张**真实月光水面**的照片（月亮居中、一条细光柱、柱内是**断续的横纹/之字形**）：

> 「月光整体我觉得要大改，**在正中央不要动**，月光柱要细，**照出水的纹理**。
>  另外水的纹理现在不够好看，看看能不能改成[参考图]这样的**横纹 / 之字形**。」

**本轮主控诊断的新结论 —— 这三件事是同一个根因的三面**：

`swDetail`（`60-water.js:88-135`）的 16 个波，方向是**各向同性随机**（`(slot[i]+0.5+0.7·rng)/N·TAU` 均匀覆盖 0~2π）。这导致：

- **水纹**：随机方向的波叠加 ⇒ **碎网**（不是横纹）
- **月柱**：横向坡度与纵向坡度同分布 ⇒ 镜面高光在**横向散开** ⇒ 柱变一大片
- **湖底扭曲**：折射位移 `off` 也是各向同性 ⇒ 湖底被「揉」而不是被「荡」

**实测（`_wavedir2.mjs`，不改源码 —— 运行时替换 `fragmentShader` 里的 `swDetail` 块再 `needsUpdate`，真实渲染）**：

| 候选 | 方向分布 | 柱宽(2σ) | **横纹比** E\|∂y\|/E\|∂x\| |
|---|---|---|---|
| S0 现状（各向同性） | 0~360° 均匀 | 43.8% | **1.53** |
| S1 单向 ±22° | 全压到 90° | 36.6% | 3.58 |
| **S2 双向 ±22°**（两组反向行波 → 拍 → **成群的短横纹**） | 90°/270° 两组 | 36.2% | 3.41 |
| S3 双向 + 之字形（相位沿 x 摆动） | S2 + zigzag | 36.9% | 3.09 |
| S4 双向 ±10°（更窄） | S2 更窄 | **34.2%** | **4.33** |

⚠ **口径警示（吸取本项目已踩过的坑）**：上一轮曾把 `uProbe=8` 的「高光区域占比 79%」当成"成品有 79% 的高光区域"——**这是探针语义的假象**（`uProbe=8` 在 `fog_fragment` 之前 return，把**每个水面像素**的 `D·Vis·Fs` 都写出来，等于把整张水面都点亮了）。**柱宽与横纹比两项是成品画面直接量的，可信；「高光区域占比」那一列已从本版删除。**

**成品观感**（`plan/shots-up4/pv-wavedir-full.png` 三格全画面 · 午夜 22:30）：

- **S1 单向** = 百叶窗（太规则，**不推荐**）

## §2 变更内容（候选，待拍板）

### A · bloom 收窄（已验证的正杠杆）—— `65-post.js` / `00-config.js`

`bloomStrength .55 → 0.25~0.35` · `bloomThreshold 0.85 → 1.05~1.15` · `bloomRadius 0.40 → 0.25~0.32`
- 实测收益：整幅均值 −6%~−9%、**近端 132→113（−14%）**、观感上"不再糊成一片"
- ⚠ **正午几乎不受影响**（正午 spec 0.68，没有可 bloom 的东西）⇒ 这条**只治夜景**，正是我们要的
- ⚠ `bloomThreshold` 抬高会让**只有反光柱**被 bloom 吃到 → 白天完全无变化，**保住了 UP12 的白天成果**

### B · 反光纵向整形（实现「从远到近」）—— 新参数 + `60-water.js`

给反光项加一个**随视线距离的权重**：

```
w(d) = clamp((d − d0) / (d1 − d0), 0, 1) × (wFar − wNear) + wNear
col += uGlitterColor * uGlitterGain * uSunRadiance * (D * Vis * Fs) * w(d)
```
- `d` 可由现有的 `vViewPos` / `uCamPos` 求（shader 里已有世界坐标口径，**无需新增 varying**）
- 建议 `d0 = 5 m` · `d1 = 22 m` · `wNear = 0.45` · `wFar = 1.30`
  ⇒ 近端降到 45%、远端抬到 130% ⇒ 直接把峰值从"中段"搬到"远端"
- 落成 `00-config.js §6` 的 **`glitterDistNear` / `glitterDistFar` / `glitterGainNear` / `glitterGainFar`** 四个字段
  （或合并成两个 `[near, far]` 区间字段，由施工方定）

### C · 夜间反光总量克制 —— `20-time.js` 的 `gGain`

`22.5 星夜 1.20 → 0.75~0.90` · `2.0 子夜 1.15 → 0.72~0.85` · `18.5 黄昏 0.35 → 0.28` · `5.5 晨雾 0.30 → 0.26`
- 🔴 **硬下限**：断言 **#7** 要求 `uGlitterGain(22.5) > 0.5` ⇒ **夜间 `gGain` 不得 ≤ 0.50**（现在 1.20，最多降到 0.55 左右）
- ⚠ 单独降 `gGain` 会**同时压低** `#13` 的 `peak/median`（分母是水面基础亮度，不随 `gGain` 缩）⇒ **必须复测**

### D · 晨昏低仰角白带（次要，但 UP12 之后会**变显眼**）

晨雾/黄昏的镜面在 24° / 22° 仰角下天然极强（AM-003 记录 `shape`：22°→7.63 · 28°→2.50）。
- 现状 `gGain` 已很低（0.30 / 0.35），所以只能靠 B 项的整形或 D 单独压低
- 🔴 **重要依赖**：**UP12 降雾之后，这条白带会突然显眼**（雾本来盖着它）⇒ **UP13 不是可选项，是 UP12 的必要跟班**

> 📖 **给雨桐解释"晨昏白带"是什么**：日出/日落时段（晨雾 h=5.5 / 黄昏 h=18.5）太阳仰角只有 22~24°，
> 镜面点在 `4.35/tan(22°) ≈ 10.8 m`（画面中远处）。低仰角下法线分布的长尾在**横向**铺开 ⇒
> 太阳的镜面高光不是一条竖柱，而是**横贯画面的白带**。现在被浓雾盖住看不太清，
> UP12 降雾之后它就会突然变显眼 —— 所以叫"UP13 是 UP12 的必要跟班"。

### E · 🔴 波表方向重铸（**本包主杠杆**，2026-09-25 新增）—— `60-water.js`

**一条改动同时解决雨桐的三条抱怨**：水纹难看 / 月柱太宽 / 高光区域太大。

做法：把 `DETAIL` 表的 16 个波的方向从**各向同性**改成**双向定向**：

```
原：ang = (slot[i] + 0.5 + 0.7*rng()) / N * TAU     // 0~2π 均匀
新：base = (u0 < 0.5) ? 0.25 : 0.75                 // 两组反向行波（90° / 270°）
    u    = base + ((u0*2)%1 - 0.5) * 2 * spread      // spread = 0.122 ⇒ ±22°
    ang  = u * TAU
```
波数 `k`、幅度 `amp`、相位 `ph`、色散 `om`、归一化 `norm` **一字不动**（只改方向 ⇒ `sumS`/`norm` 不变 ⇒ `uGlitterDetail` 的量纲不变）。

再加（可选）**之字形**：给每个波的相位塞一条低频横向正弦
```
ph' = ph + zigA * sin(p.x * zigFreq + ph)      // 建议 zigA ≈ 0.85 · zigFreq ≈ 0.75
```
⇒ 波峰线从「完美水平直线」变成「左右摆动的曲线」—— 参考图的「之字形」来自这一项。

**落成 `00-config.js §6` 的三个字段**：`waveSpread`（默认 0.122）· `waveZigA`（默认 0.85 或 0 关闭）· `waveZigF`（默认 0.75）。
⚠ `DETAIL` 是**模块加载时**算好的编译期常量（`60-water.js:88-117`），改字段后要**刷新页面**才生效
（或临时加 `?wavedir=` 调试入口 —— 这条要写进 `03-COLLAB-PROTOCOL §7.2`：**改了参数必须真的刷新**，
否则会重演「静默失效」）。

**量化收益（真实渲染实测，见 §1.6）**：

| | 现状 | S2 | S3 | S4(±10°) |
|---|---|---|---|---|
| 柱宽 2σ | 43.8% | 36.2% | 36.9% | **34.2%** |
| 横纹比 | 1.53 | 3.41 | 3.09 | **4.33** |

**为什么 E 是主杠杆、A/B/C 都是配角**：
- A/B/C 都是**事后补救**（把"一大片"压暗/压窄）；E 是**让高光在几何上就集中到一条柱**。
- E 顺带把水纹变成参考图的样子 —— A/B/C 做不到这一点。
- bloom（A）在 E 之后**作用面变小**（要 bloom 的亮区小了）⇒ **A 的幅度建议放到 E 之后**再定档，而不是反过来。

**E 与既有结论的关系**：
- 与 §1.5「`glitterDetail` 收窄是负杠杆」**不冲突** —— 那条是"幅度"，E 是"方向"，两个正交。E 落地后 `glitterDetail` **保持 0.16 不动**（§5）。
- 与 §2-B「纵向整形」**正交** —— E 管"柱多细"，B 管"柱的能量沿 y 怎么摆"，都要做。
- 与 **UP12 §2-C 折射** 强相关 —— 见 §1.6 尾部。

**E 的已知边界**：
- **白天几乎无效**（实测正午 σ 11.9 → 12.0，肉眼不可辨）⇒ E 是**夜间课题**，白天不受影响（好：UP12 的白天成果保住）
- ⚠ **交互涟漪（`sR`）仍是各向同性** —— 用户点击/拖动时的涟漪会与定向 `sD` 叠加，可能"打破"横纹（自然还是突兀要实测；若突兀，给 `sR` 加"定向权重"或降交互时的 `sD` 占比 —— **另立小包，不在本包范围**）
- ⚠ 波表方向变了 ⇒ `#3` 折射差分 / `#6` 湖底对比 / `#13` 柱形，**三条都要复测**
