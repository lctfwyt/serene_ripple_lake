# 03 · 多窗口协作写入纪律

> 背景：`_STATUS.md` v1 失控（844 行）—— 各窗口把整段报告塞进状态表一行，断表、上下文爆炸。
> 本文件定义**谁往哪写什么**。历史快照：`98-STATUS-ARCHIVE-v1.md`（v1）· `98c-SLIM-ARCHIVE-20260925.md`（v2，含本文件瘦身前全文与环境坑完整排查记录）。

---

## 1. 文件分工（一张表说清）

| 你想写的东西 | 写到哪 | 绝不写到 |
|---|---|---|
| 「我做完了」+ 关键读数 | `plan/_STATUS.md` **追加一行** | — |
| 过程、数据表、诊断、复盘、试错留档 | 本包文档追加 `## 完工记录`，或新建报告 `plan/<n><包名>-report.md` | `_STATUS.md` |
| 改共享常量 / 跨包约束 / 规格变更 | `plan/02-AMENDMENTS.md` 开变更单（唯一通道） | `_STATUS.md` 正文 |
| 裁决结论（谁拍的板、改了什么） | 变更单内；`_STATUS.md` 只改状态列 | 新开一节长文 |
| 问主控 / 提醒别人 / 口头决定 / 阻塞求助 | `plan/04-BOARD.md` 留一行（≤40 字） | `_STATUS.md` / 变更单 |
| 临时脚本 / 诊断帧 | 根目录 `_*.js` / `_*.png`，交付前删或归档 | plan/ 编号文件 |

**原则：`_STATUS.md` 是台账，不是档案。** 台账行像 git log 的一行摘要，档案在别处。

## 2. `_STATUS.md` 的行格式（硬性）

| 规则 | 要求 |
|---|---|
| 一包一行 | 多轮返工**合并成一行**，写最终态 |
| 一句话结论 | **≤ 60 字**。只写最终结果，不写根因推导 |
| 遗留 → 去向 | 每条 ≤ 40 字 + 指向：挂到哪个包 / 哪份变更单 / 已关闭 |
| 禁止 | 行内嵌套表格、`<br>` 换行、成段文字、多段落单元格 |
| 追加不改历史 | 已有行不动；新信息 = 新一行或改状态符号 |
| 遗留被解决 | 只在状态列加 ✅ / 编号指向裁决，不重写原文 |

## 3. 变更单的生命周期（防止 02-AMENDMENTS.md 二次失控）

| 阶段 | 存放 |
|---|---|
| ⬜ 未决 / 🔶 部分应用 | **全文放在 `02-AMENDMENTS.md`**（活跃文档，需完整可执行） |
| ✅ 全部应用并验证 | 全文**移入归档**（`98b-AMENDMENTS-ARCHIVE-v1.md` 追加），总表只留一行 |
| 改写了旧口径 | 在 `02-AMENDMENTS.md §3` 改写关系速查表加一行，**废除的口径写明** |

归档命名沿用 `98x-*-ARCHIVE-*.md` 系列；大快照统一进 `98c-SLIM-ARCHIVE-20260925.md` 追加节。

## 5. 留言板 `04-BOARD.md`

- **按收件人分段**：`全体`（广播必读）· `主控` · `<包名>`。一行 ≤40 字，回复新起一行、不改原文，处理列 ⬜→✅/→AM-xxx。
- **一眼定位**：每个窗口**只读自己的箱 + 全体箱**；顶部收件箱目录一眼扫完。
- **想改别人的规格/文件 → 不走留言板**，开变更单是唯一通道；板上消息标 `→ AM-xxx` 即闭合。
- **两条铁律**：写完留 ⬜ 不许自答自关；自己箱里的 ⬜ → **先处理再干活**，收尾清零。
- **归档**：单箱超 ~20 行 → 整箱移入归档，目录标记「已归档」。

## 6. 报告文件的命名

| 类型 | 命名 | 例 |
|---|---|---|
| 主控复核 / 专项报告 | `<序号><a-b>-<名>-report.md` | `90a-UP8-report.md` |
| 包完工记录（首选） | 追加进包文档 `## 完工记录` | `91-UP5-audio.md §8` |
| 裁决 | `02-AMENDMENTS.md` 新 AM 条目 | AM-012 |

## 7. 各窗口的开场与收尾

**开场**（雨桐复制）：`@plan/00-INDEX.md @plan/01-CONTRACT.md @plan/02-AMENDMENTS.md @plan/03-COLLAB-PROTOCOL.md @plan/04-BOARD.md @plan/<本包>.md`

**收尾四步**（缺一不可）：
1. 包文档追加 `## 完工记录`
2. `_STATUS.md` 追加一行（§2 格式）
3. 有跨包影响 → 先开变更单，再收尾；**没有变更单就没有跨包改动**
4. 板上指向自己且未处理的 ⬜ → 全部处理并标 ✅（或开 AM）

### 7.1 提交纪律（git）

| 模式 | 情形 | 谁提交 |
|---|---|---|
| **A · 独占** | 本轮只有你一个包在工作区 | **你自己提**：`feat(upN): <做了什么>（AM-0xx）` |
| **B · 并行** | 同波次有 ∥ 的包（共用工作区） | **都别提交**，裸改动留主控复核后统一提 |

两种模式都适用：
1. 只 `git add` 自己白名单里的文件、**逐条列名**；**禁 `git add -A` / `git add .`**（并行会带上别包半成品）。
2. 不许 `--amend` / `--force` / `--no-verify`；不许动 tag；不许改 `90-WAVE4.md`（只读口径）。
3. **基线类文件不许自己重录**：`plan/pw/**`（三条 png + dist-baseline.txt）是主控地盘，红了报主控。
4. 提交信息必须带 AM 号；提交后把 `git log -1 --stat` 贴进完工记录。
5. 主控复核发现问题 → 追加返工提交，**不 amend** 原提交（留作历史证据）。

### 7.2 同上下文施工时的证据要求

规划与施工同方时，三条强制：
1. 包文档完工记录**必须标注**「本包无独立复核方，复核为同上下文自证」——不许写「复核通过」。
2. 必须给**机械可验证的独立证据**：冻结件 sha256 前后一致 · HEAD 副本逐位等价证明 · 阈值扫描 · 白名单越界核查 · 正反两面都测（该变的变了 + 不该变的一字未动）。
3. **审美/取向类结论一律挂验收**，施工方不得自行判定通过。数值判据可自证，"好不好看"不行。

**口径纪律**：
- **跨候选比较必须走冷启动**（各起一次页）。会话内切换参数的读数会漂 ~0.6（实测同配置 15.38/14.74/14.36，冷启动 14.95）；调试滑杆只用于看方向。冷启动 A/B 做法见 98c §④。
- **凡「改 A 再量」必须先证明 A 真的被改掉了**（有被 `applyTimeState` 每帧回写静默吞掉的先例，结论曾完全反转）。
- **探针 ≠ 成品**（`uProbe=8` 是探针饱和假象；且 `uProbe` 只在 `?debug=1` 编译进 shader，非 debug 起页静默无效）。

**五条反面教训**（全文见 98c §④）：
1. 诊断图缩略图的采样精度本身是口径 —— 判断细节一律 1:1 或最近邻放大。
2. 别拿冻结判据的余量换审美；"地板"不一定是下限（AM-020/021 两次实证）。
3. 判据指标向好 ≠ 观感向好（"只亮不暗"判据最优却被雨桐否决）。
4. 降 `bedRoughVar` 拿余量是陷阱：`#6` 假升但画面 std 反升 1.8% —— 观感与 `#6` 负相关。
5. 凡"观感"结论：判据读数只能当筛子不能当裁判；必须用带后期的最终画面量，不是中间产物。

### 7.3 派包机制：依赖分析 → 平行/串行判定 → 出开场白

| 步 | 动作 | 产出 |
|---|---|---|
| ① | 依赖分析：每包改哪些 `src` 文件、前置包、会不会让冻结判据失去对象 | 依赖表 |
| ② | 平行/串行判定（下表） | 波次划分 |
| ③ | 出开场白（每包一段，雨桐整段复制进新聊天框） | 可粘贴文本 |

| 情形 | 判定 |
|---|---|
| 两包改同一文件 | 串行 —— 后包等前包提交后再开 |
| 改不同文件 + 无前置依赖 | ✅ 可平行 —— 同波次一起派 |
| 有数据/接口依赖 | 串行 |
| 会让某条冻结判据失去对象 | 单独排，**先开变更单重构判据**再开工 |

**开场白模板**（沿用 §6 的 `@` 串，后接四段任务说明）：

```
@plan/00-INDEX.md @plan/01-CONTRACT.md @plan/02-AMENDMENTS.md @plan/03-COLLAB-PROTOCOL.md @plan/04-BOARD.md @plan/<本包>.md

你是「<包名>」的施工方（不是主控）。开工前先读完 @ 文件，再读本包文档。
- 你的文件（一票否决级所有权）：<文件列表>
- 前置：<前置包 ✅ / 无> · 并行：<并行包>（不许碰它负责的文件）
- 变更单：<AM-0xx>
- 收尾四步（§7）：完工记录 → _STATUS 一行 → 跨包影响先开 AM → 板上 ⬜ 清零
- 提交：模式 <A 独占 / B 并行>，信息带 AM 号，git add 逐条列名（禁 -A）
- 验收：审美/取向类结论一律挂验收，你不得自行判定通过（§7.2-3）
```

**主控派包后必须做**：波次划分写进 `00-INDEX` 波次表 + 在 `04-BOARD` 对应包箱留一行。

## 8. 本机环境坑（会反复咬人，先记下）

### 8.1 pw 残留撑肥 safe-delete 守卫 —— 已从源头消除

根因是 `trace:'retain-on-failure'` 的 **screencast 逐帧录像**（1375 帧 / 75 MB）没清干净，不是"条目太多"。
修法（`plan/pw/playwright.config.mjs` 一行）：

```js
trace: { mode: 'retain-on-failure', screenshots: false },   // 关 screencast，保 trace.zip
```

残留 1378→14 条目 / 75 MB→125 KB；**直接 `npm run pw`，不需要 `--output` 绕法**。
守卫阈值雨桐已调 9999（现非瓶颈，不建议再调高——个人目录共享同一阈值）。完整排查记录见 98c §④ §8.1。

### 8.2 pw 像素门的四条盲区（它不是变更门禁，是哨兵）

1. **threshold 0.2 ≈ 37.5 级/通道**：`d = 0.29889531·Δr² + 0.58662247·Δg² + 0.11448223·Δb² > 35215×0.2²` ⇒ 三通道同向差需 Δ > √1408.6 ≈ 37.5 级。实测贴图改动 49% 像素变、最大差 29 级 → **0 px 超阈**。画面变化的证据要用专项量化（逐像素直方图 + 阈值扫描）或断言读数位移。
2. **`includeAA:false` 的 AA 启发式依赖基线内容**（AM-018）：孤立坏像素可能被当反锯齿丢弃，换基线就翻面 → 哨兵注入用 **3×3 块**；**基线重录后必须复跑 pw 全链含哨兵**。
3. **`pw:update` 是 `changed` 模式**：不改写"没红但已陈旧"的基线，要 `--update-snapshots=all`。
4. **`boot()` 全程不发手势**：需手势才激活的 UI（如 `#sw-bgm` 选中态）零覆盖；且 `threshold 0.2` 下半透明 UI 变更 2866 px→8 px —— **别把 `full.png` 当 UI 门禁**，要守 UI 用定位到元素的基线。

**方法论**：量"改前 vs 改后"的正确口径是 **Playwright 截图（合成帧）**，不是裸渲染 `readPixels` —— 裸渲染里湖底被水面挡住、只透过折射 RT 可见，而 `sceneRT` 只在完整 `SW.scene.render()` 步骤①刷新 ⇒ 裸渲染对湖底材质变化完全不敏感（实测 `hideLakebed→0 差异`）。

### 8.3 报"pw 全绿"时的规范说法

说「**哨兵与确定性未退化；门内无超阈像素**」—— 不要说"画面没变"。想收紧门必须显式调 `threshold`/`maxDiffPixels` 或另开基线，属产品取向，须走变更单，不能顺手改。
