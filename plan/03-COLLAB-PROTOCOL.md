# 03 · 多窗口协作写入纪律

> 背景：`_STATUS.md` v1 失控（844 行）—— 各窗口把整段报告、嵌套表格、诊断复盘
> 全部塞进状态表的一行里，导致断表、无法浏览、上下文爆炸。本文件定义**谁往哪写什么**。
> 归档：`98-STATUS-ARCHIVE-v1.md`（v1 全文，只读不改）。

---

## 1. 文件分工（一张表说清）

| 你想写的东西 | 写到哪 | 绝不写到 |
|---|---|---|
| 「我做完了」+ 关键读数 | `plan/_STATUS.md` **追加一行** | — |
| 过程、数据表、诊断、复盘、试错留档 | 本包自己的文档（如 `20-WP2-….md` 追加 `## 完工记录` 节）或新建报告 `plan/<n><包名>-report.md` | `_STATUS.md` |
| 改共享常量 / 跨包约束 / 规格变更 | `plan/02-AMENDMENTS.md` 开变更单（唯一通道） | `_STATUS.md` 正文 |
| 裁决结论（谁拍的板、改了什么） | 变更单内；`_STATUS.md` 只改状态列为 ✅ | 新开一节长文 |
| **问主控 / 提醒别人 / 口头决定 / 阻塞求助** | `plan/04-BOARD.md` 留一行（≤40 字） | `_STATUS.md` / 变更单 |
| 临时脚本 / 诊断帧 | 根目录 `_*.js` / `_*.png`，交付前删或归档 | plan/ 编号文件 |

**原则：`_STATUS.md` 是台账，不是档案。** 台账行像 git log 的一行摘要，档案在别处。

---

## 2. `_STATUS.md` 的行格式（硬性）

```md
| 包 | 完成时间 | 状态 | 一句话结论 | 遗留 → 去向 | 详情 |
```

| 规则 | 要求 |
|---|---|
| 一包一行 | 多轮返工（WP4-fix / WP4-flow2…）**合并成一行**，写最终态 |
| 一句话结论 | **≤ 60 字**。只写最终结果，不写根因推导 |
| 遗留 → 去向 | 每条 ≤ 40 字 + 指向：挂到哪个包 / 哪份变更单 / 已关闭 |
| 详情列 | 链接：包文档锚点或报告文件名 |
| 禁止 | 行内嵌套表格、`<br>` 换行、成段文字、多段落单元格 |
| 追加不改历史 | 已有的行不动；新信息 = 新一行或改状态符号（⬜→✅） |
| 遗留被解决 | 只在状态列加 ✅/编号指向裁决（如 `→ AM-006 已关`），不重写原文 |

## 3. 变更单的生命周期（防止 02-AMENDMENTS.md 二次失控）

| 阶段 | 存放 |
|---|---|
| ⬜ 未决 / 🔶 部分应用 | **全文放在 `02-AMENDMENTS.md`**（此时它是活跃文档，需要完整可执行） |
| ✅ 全部应用并验证 | 全文**移入归档**（`98b-AMENDMENTS-ARCHIVE-v1.md` 追加），总表只留一行（编号/日期/一句话/影响/状态） |
| 改写了旧口径 | 在 `02-AMENDMENTS.md §3` 改写关系速查表加一行，**废除的口径写明**，防止后来者用回旧值 |

归档文件命名沿用 `98x-*-ARCHIVE-v1.md` 系列；新归档在其后追加节，不另开文件。

## 5. 留言板 `04-BOARD.md`

- **定位**：主控 ↔ 分包的轻量传话通道。**按收件人分段**：`📥 全体`（广播必读）· `📥 主控` · `📥 <包名>`。一行 ≤40 字，回复新起一行、不改原文，处理列标 ⬜→✅/→AM-xxx。
- **一眼定位**：每个窗口**只读自己的箱 + 全体箱**——看顶部收件箱目录就知道有没有自己的事，别人的箱不进上下文。
- **想直接改别人的规格/文件 → 不走留言板**，开变更单（AM）才是唯一通道；板上消息标 `→ AM-xxx` 即闭合。
- **两条铁律**：写完消息把处理列留 ⬜（等对方处理，不许自答自关）；自己箱里的 ⬜ → **先处理再干活**，收尾时清零。
- **归档**：单箱超 ~20 行 → 整箱移入归档文件，目录标记「已归档」。

## 6. 报告文件的命名

| 类型 | 命名 | 例 |
|---|---|---|
| 主控复核 / 专项报告 | `<序号><a-b>-<名>-report.md` | `90a-UP8-report.md` |
| 包完工记录（首选） | 追加进包文档 `## 完工记录` | `91-UP5-audio.md §8` |
| 裁决 | `02-AMENDMENTS.md` 新 AM 条目 | AM-012 |

## 7. 各窗口的开场与收尾

**开场**（由雨桐复制）：`@plan/00-INDEX.md @plan/01-CONTRACT.md @plan/02-AMENDMENTS.md @plan/03-COLLAB-PROTOCOL.md @plan/04-BOARD.md @plan/<本包>.md`

**收尾四步**（缺一不可）：
1. 包文档追加 `## 完工记录`（过程与数据都在这）
2. `_STATUS.md` 追加一行（§2 格式）
3. 有跨包影响 → 先开变更单，再收尾；**没有变更单就没有跨包改动**
4. 板上指向自己且未处理的 ⬜ 消息 → 全部处理并标 ✅（或开 AM）

### 7.1 提交纪律（git）

> 依据：`00-INDEX §7`「每包完成即提交一次」+ `90-WAVE4 §6` ⑤⑥。
> 此处**收拢**这两条，并补上原文档没写、却真实发生过的**并行波次**情形。

**第一步先判自己属于哪种模式**（拿不准就问主控，别自己猜）：

| 模式 | 情形 | 谁提交 |
|---|---|---|
| **A · 独占** | 本轮**只有你一个包**在工作区 | **你自己提**：`feat(upN): <做了什么>（AM-0xx）` |
| **B · 并行** | 同一波次有 ∥ 的包（**共用同一工作区**） | **都别提交**，裸改动留给主控复核后统一提 |

> **为什么要有模式 B**：并行时 `git status` 里必有对方的改动，「只剩自己的文件」**不可满足** ——
> `90-WAVE4 §6-⑥` 没写这种情形怎么办，实际结果就是两包都提不了、最后由主控代提（UP9∥UP10 即如此，
> 见 `1294b52`）。**这条路是对的，只是当时没明写**，害得复核要靠 `reflog` 反推"这是裸改动不是提交过"。

**两种模式都适用**：

1. 🔴 **只 `git add <自己白名单里的文件>`，逐条列名。禁止 `git add -A` / `git add .`**
   —— 并行时会把**别的包的半成品**一起提进去。
   （临时件 `_*.js` / `_*.png` 已被 `.gitignore §9` 挡掉，但别人的 `src/**` 挡不住。）
2. **不许** `--amend` / `--force` / `--no-verify`；**不许动 tag**（`baseline-pre-tier12` 是回退点）；
   **不许改 `plan/90-WAVE4.md`**（只读口径）。
3. **基线类文件不许自己重录**：`plan/pw/**`（`full.png` / `ui-panel.png` / `bed-clip.png` / `dist-baseline.txt`）
   是主控地盘。测试红了 → **报主控**，别自己 `--update-snapshots`。
4. 提交信息**必须带 AM 号**；提交后把 `git log -1 --stat` 原文贴进包文档完工记录。
5. 主控复核若发现问题 → **追加一个提交返工，不 amend 你那个** —— 你那个提交留作「被复核对象」的历史证据。

## 8. 本机环境坑（会反复咬人，先记下）

### 8.1 pw 的 safe-delete 守卫 —— **已从源头消除**（2026-09-25 主控）

> ⚠️ 本节此前写的是「每跑 ~6300 条目 / 撞 5000 阈值 / 用 `--output=_pwN` 绕」。
> **那套结论已作废** —— 它不是"条目太多"，是"垃圾太多"。作废原因见下方「历史」。

**根因**：`use.trace = 'retain-on-failure'` 会对**每个用例都先录** trace、通过后再丢弃；
丢弃没清干净，`traces/screencast/*.jpeg`（逐帧录像）全留在产物目录里。

实测（2026-09-25）：

| | 改前 | 改后 |
|---|---|---|
| 单跑残留条目 | **1378** | **14** |
| 体积 | **75 MB** | **125 KB** |
| `screencast/*.jpeg` | **1375 帧** | **0** |

**修法**（`plan/pw/playwright.config.mjs`，一行）：

```js
trace: { mode: 'retain-on-failure', screenshots: false },   // 关 screencast，保 trace.zip
```

关掉的只是**逐帧录像**；`trace.zip`（DOM 快照 / 网络 / console）照旧，失败仍可查。
改后 `pw` 全链 **14 passed**，`ui-panel` / `bed-clip` / `full.png` 快照与 `dist-baseline.txt` **逐字节未动**。
剩下的 14 个条目正是**该留的** —— 30-pixel 三个哨兵用例（故意改坏像素）的 `actual/diff/expected.png`。

**所以现在直接 `npm run pw` 就行，不需要任何 `--output` 绕法。**

**阈值注记**：守卫阈值默认 5000，**雨桐可调**（2026-09-25 已调至 **9999**，实测放行）。
单跑只剩 14 条目后，阈值已不是瓶颈 —— **不建议再往上调**：那是拿「全局删档安全网」去补贴某个目录，
而个人目录（Desktop / Downloads / Documents）共享同一阈值。若哪天又撞，**先查是谁把目录撑肥了**。

**历史（留作排查别的批量删除时参考）**：撞守卫时错误形如
`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":6308,"threshold":5000,...}`。
两个反直觉点：① 守卫数的是「**条目数**」（含目录，**不是文件数**）—— 目录里实际只剩 1387 个文件时它照样报 5376；
② **一旦撞过，同一轮对话内对同一路径会一直报同一个数**（清干净也不管用）。
在那时，绕法是 `--output=test-results/_pwN`（快照落点由 `snapshotPathTemplate` 决定、**与 `outputDir` 无关**，
所以基线照样写进 `plan/pw/tests/__snapshots__/`；UP9 当年靠「把 `test-results` 改名」绕过）。
「第二次起必被拦」的真实机制是：**守卫拦的是「下一次运行启动时清理上一次残留」这个动作** ——
残留 75 MB 在那儿，下一次运行一启动就要删它，于是撞。

### 8.2 `full.png` 像素基线对半透明 UI 变更**几乎不设防**

Playwright `toHaveScreenshot` 默认 **`threshold: 0.2`**（逐通道感知容差）——
`#sw-bgm` 的 chip 底 `rgba(255,255,255,.20)` 叠在浅水色上，逐通道差够不到 0.2，
**2866 px 的原始差异过容差后只剩 8 px**。→ **别把「8 px」读成「没改」，也别把 `full.png` 当 UI 变更的门禁。**
真要守 UI，用 `ui-panel.png` 那种「**定位到元素**再截图」的口径，或给新控件单开一条基线。

### 8.3 pw `boot()` 全程不发手势 ⇒ 需要手势才激活的 UI **零覆盖**

`30-pixel.spec.mjs` 的 `boot()` 从 `page.goto` 到截图**不发任何手势**，而 `SW.audio.init()`
只在首次手势后调用（`99-main.js` ④）→ pw 环境下 `#sw-bgm` 的 chip **永远不进 `.on` 选中态**。
影响：无随机 → 无 flake（好），但「哪枚被选中」这件事**没有任何基线覆盖**（真机必有高亮）。

> ⚠ **§8.2 的盲区还有第二层**（2026-09-25 补，见 §8.4）：差异**过了** `threshold 0.2`
> 的**孤立**像素，仍可能被比较器的反锯齿启发式丢掉。两层叠加，就是 UP3 那种
> "98~100% 像素改变 / **0** 像素超阈"的极端读数。

### 8.4 重录像素基线会**悄悄改变哨兵灵敏度**（`includeAA:false` + AA 启发式）

**背景**：`30-pixel.spec.mjs` 的三条哨兵靠"注入坏像素 ⇒ 断言必红"来证明像素门不是摆设。

**事实（2026-09-25 主控实测，AM-018）**：Playwright 的 `toHaveScreenshot` 走**内置 pixelmatch**，
默认 `includeAA: false` ⇒ **判为反锯齿的差异像素不计入 diff**；而该判定依据
**该像素在两张图里的邻域极值 + `hasManySiblings()`** ⇒ **依赖基线在该处的实际像素值**。

> **同一个孤立坏像素、同一帧、同一进程，只换基线文件 —— 旧基线"检出"、新基线"漏检"。**
> （真实 A/B：旧基线 `1 pixels (ratio 0.01 …) are different` → 哨兵 passed；
> 新基线 `threw = null` → 哨兵 failed。sim 复算同结论：δ 都远超 `maxDelta=35215×0.2²=1408.6`，
> 差别只在 AA 分类。）

**三条可操作的推论**：

1. **哨兵注入别用 1 px** —— 用 **3×3 块**（块内有 ≥3 同色邻居 ⇒ 必然不被判 AA ⇒ 与基线内容无关）。
   尺寸扫描实测：1×1 → `1 px / 0 px`；2×2 → `4 / 2`；**3×3 → `6 / 6`**；4×4 → `12 / 12`。
   （已落进 `lib/page-lib.mjs` 的 `breakPixelsSnippet`，默认 3×3。）
2. **`npm run pw:update` 是 `changed` 模式 —— 只改写"失败"的快照**。一张**没红但已陈旧**的基线
   **不会**被它重写（UP3 的 `full.png` 就踩了这个：它已是 UP3 之前的画面，却因差 1/255 而绿着）。
   要重录这种，必须 `--update-snapshots=all`。
3. **基线重录后必须复跑 `pw` 全链**（含哨兵），别只看"PASS"就收工 ——
   重录可能刚刚把你的哨兵弄哑。规范：**基线重录属主控动作（§7.1-③），重录后要有一次全链复跑留痕。**
